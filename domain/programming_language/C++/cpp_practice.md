## 1.1 设计不出来的真正原因

设计不出来不是能力问题，是方法顺序错了。设计不是写代码之前要做的事情——恰恰相反，设计是写完代码，感受到不舒服之后才会浮现的东西。现在困境是经典的设计真空。emmm，真空好久了。所谓真空就是：没有代码、没有约束，却要求自己要画出比较完美的图纸，这当然是天方夜谭。

上述的根因可以拆为三点：

1. 真空里无法设计：设计本质是"在约束之间做取舍"，没有约束（性能、内存、扩展需求）就没有取舍，就没有形状。空想"一个 git 客户端怎么设计"永远无从下手；但"扫描 1 万个文件不能卡 UI"立刻会逼出设计。

2. 设计词汇不够：你不知"形状"有哪些（10 个常用模式），就无法识别"这个痛苦长得像装饰器/策略/观察者"。读代码能看懂，是因为形状已在那里；自己造时没有形状可用。

3. 想一次设计完美：C++ 让你害怕返工（所有权、值语义改起来痛），于是过度设计来"预防"——结果变成永远在设计。

## 1.2 心态转变

**设计=重构的积累**

不需要先设计，而是先烂，再感受到了烂，浮现的设计。

事情就是这样，频繁做，频繁做...频繁做，直到有一天，真正的答案浮现在了眼前，这就是设计，同样也是人生设计。

1）抽象永远晚一步出现，而不是预防性的先抽象，抽象植根于现实，先具体再抽象。

2）先写死，后参数化，写死很丢人吗？不，并不丢人，能够让设计信号暴露，反而是一件好事。

3）先用拷贝，再考虑共享，先用unique_ptr再shared_ptr，所有权默认往最严格的方向走，编译器会告诉什么时候该放松。

## 1.3 落不到C++

还是想用的太多了，但是没那个能力，懂吗？

所以先用机械翻译表才是王道（其他的语言也是一样），用机械翻译表去烂烂的做。

### 1 数据与容器

| 自然语言/设计里的说法 | 落成C++的什么 | 什么时候升级|
|---|---|---|
|“一组东西”|std::vector<T>|需要按 key 查找 → std::unordered_map；需要有序唯一 → std::set|
|“可能没有/可选的”|默认值+空判断 | 空值有业务语义时 → std::optional<T>|
|“要么这个要么那个”|重载/两个字段|分支超过3种std::variant<T1,T2,...>|
|“字符串处理”|std::string+自由函数|只读传递不拷贝 → std::string_view；高频拼接 → reserve()/ostringstream|
|"查找/排序/去重"|手写循环|改用 STL 算法：std::find/std::sort/std::unique（零成本且不易错）|
|“缓存/重复计算”|每次都算|实测难受——memoization / 惰性缓存|
|“一批固定常量”|魔数散落|命名 → constexpr；互斥选项 → enum class|
|“某个东西”（名词）|struct + 数据成员（先别加行为）|数据出现不变量时再加成员函数|

### 2 行为与组织

| 自然语言/设计里的说法 | 落成C++的什么 | 什么时候升级|
|---|---|---|
|“做某件事”（动词）|自由函数 dosomething(x) | 多个函数共享状态才收进类|
|“多个东西有共同行为”|复制粘贴/switch|新增一种要改动N处——基类+虚函数或concept|
|“我想让X也能被Y操作”|成员函数|对称操作，如a+b——自由函数+运算符重载；多类型通用——模板|
|“当X时做Y”|先if硬写|分支超过3个再考虑状态机/策略|
|“某些东西会通知我”|直接调用对方|不知道“谁”会监听——std::function+观察者|
|“初始化参数很多”|构造函数塞参数“|参数>5且组合多——Builder模式/设计体（Designated Initializers）|

### 3 错误与边界

| 自然语言/设计里的说法 | 落成C++的什么 | 什么时候升级|
|---|---|---|
|“可能失败”|返回bool/错误码|错误需要上下文（哪个文件、什么原因）→ 异常，或 std::expected<T,E>（C++23）|
|“不可能失败”|直接调用|明确声明 → noexcept；防止误用 → assert|
|“调用方传了非法输入”|靠文档约定|用类型系统杜绝std::span 代替裸指针+长度、强类型枚举|
|“类型转换”|static_cast/隐式|多态向下需要安全——dynamic_cast|
|“超时/重试”|同步阻塞等结果|需要限时——future.wait_for；需要重试策略——循环+退避|

### 4 并发与时间

| 自然语言/设计里的说法 | 落成C++的什么 | 什么时候升级|
|---|---|---|
|“要等一个任务”|同步调用|慢且可行——std:async/线程池|
|“后台处理完通知我”|轮询标志位|用std::future / 回调；再高级 → 协程 co_await|
|“多个地方改同一份数据”|各改各的，先别共享|必须共享——先std::mutex包住，再测热点——原子/无锁|
|“定时/计划任务”|手动sleep|需要精确调度——定时器/事件循环|

### 5 所有权与生命周期（C++独有？最重要！）

| 自然语言/设计里的说法 | 落成C++的什么 | 什么时候升级|
|---|---|---|
|“谁拥有什么”|一律先unique_ptr|真的需要共享才换shared_ptr；循环引用weak_ptr|
|“对象在函数里用一下”|栈上对象+传引用|需要传出生命周期——返回值/unique_ptr|
|“这个对象传给好几个函数”|传const&|需要修改——传非const引用；需要转移——传值+std::move|
|“一大块数据到处用”|每次拷贝|只读共享 → std::shared_ptr<const T> 或 string_view/span|
|“对象要跨线程存活”|拒绝共享，拷贝过去|真共享 → shared_ptr + 同步（先想清楚谁最后销毁）|

### 6 抽象时机

| 自然语言/设计里的说法 | 落成C++的什么 | 什么时候升级|
|---|---|---|
|“可能变化的部分”|先写死（hardcode）|难受了再加入参数化/抽接口|
|“接口/抽象层”|具体类直接调|出现第二个实现时——抽纯虚基类；只有行为无状态concept|
|“全局配置/单例”|函数参数传递|传递链太深 → 依赖注入 / 配置结构体|
|“我预感到将来要扩展”|忍住，不写|等到真实的第二个需求出现再抽象|
